title: "Securely Store API Keys as Workspace Secrets in Responder"

When an investigation needs to call an external API — for example, an internal metrics service, a feature-flag provider, or a proprietary data store — you need a way to supply credentials securely. Workspace secrets solve this by storing encrypted credentials that Responder injects as environment variables into investigation sandboxes at runtime. The secret value never appears in agent instructions, investigation traces, or logs.

## What workspace secrets are

A workspace secret is a named credential stored encrypted in Responder. When an Agent that references the secret runs an investigation, Responder injects the secret into the sandbox as an environment variable. The agent's code tools and HTTP calls made inside the sandbox can then access the credential without it ever being written into the prompt or visible in the trace.

## Why use secrets instead of embedding keys in instructions

Putting an API key directly in the Agent instructions field means the key appears in plain text every time Responder logs the instructions used for an investigation. Anyone with access to the investigation trace can read it.

Workspace secrets keep the value out of the prompt entirely. The agent's sandbox environment receives the key as an environment variable (`process.env.MY_API_KEY`, `$MY_API_KEY`, etc.), and the secret value is never shown in the dashboard after the moment of creation.

## How secrets work

1. You create a secret with a **name**, a **value**, and a list of **allowed hosts**.
2. Responder stores the value encrypted and associates it with your workspace.
3. When a secret is added to an Agent and that Agent runs an investigation, Responder injects the secret into the investigation sandbox as an environment variable.
4. The `allowedHosts` field acts as a security boundary: Responder only forwards the secret to HTTP requests that target one of the listed hostnames. Requests to other hosts are not blocked, but the secret is not attached.

<Warning>
  Allowed hosts are the authorization boundary for secret access. Always restrict the allowed host list to the minimum set of hostnames the Agent actually needs to reach. Overly broad wildcards (for example, `*`) defeat the purpose of the boundary.
</Warning>

## Allowed hosts format

Specify hostnames without a scheme, path, or port. Examples:

```text
api.example.com
metrics.internal.corp
*.datastore.example.com
```

Each entry matches requests to that exact hostname (or, with a leading `*.`, to any subdomain of the base domain). You can add up to 20 allowed hosts per secret.

## Creating a secret

<Steps>
  <Step title="Open the Secrets section">
    Navigate to **Agents** in the sidebar, then click **Secrets** in the sub-navigation. Alternatively, open any Agent's settings page and scroll to the **Secrets** section.
  </Step>

  <Step title="Enter a name">
    Enter the secret name using uppercase letters, digits, and underscores. The name must match the pattern `[A-Z_][A-Z0-9_]*` — it can start with an uppercase letter or an underscore, and can be up to 80 characters long. For example: `INTERNAL_METRICS_API_KEY`. The name becomes the environment variable name inside the sandbox.

    The UI will warn you if you enter a reserved name. Reserved names are used by Responder internally and cannot be overridden.
  </Step>

  <Step title="Enter the secret value">
    Paste the API key, token, or credential value. The value can be up to 65,536 characters.

    <Warning>
      The secret value is shown only at creation time. Responder does not display it again after you save. Copy it somewhere safe before creating the secret if you need to retain a copy.
    </Warning>
  </Step>

  <Step title="Add allowed hosts">
    Enter at least one hostname that Responder is permitted to attach this secret to. Add multiple hosts on separate lines or separated by commas.
  </Step>

  <Step title="Create the secret">
    Click **Create**. The secret is stored encrypted and appears in your workspace's secret list with its name and allowed hosts (but not its value).
  </Step>
</Steps>

## Adding a secret to an Agent

Open the Agent's settings page. In the **Secrets** section, select the secret from the list of available workspace secrets. An Agent can reference up to 20 secrets.

Save the Agent. All future investigations run by that Agent will have the selected secrets injected as environment variables.

## Rotating a credential

<Note>
  Secrets cannot be updated after creation. To rotate a credential, create a new secret with the updated value, update the Agent to reference the new secret, and remove the old secret from the Agent. Delete the old secret record once you have confirmed that investigations are using the new one.
</Note>

This approach gives you a brief window during which both the old and new secrets exist, making it safe to roll back if the new credential is invalid.
