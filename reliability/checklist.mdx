## Set it up with one prompt

<Steps>
  <Step title="Connect the agent to Superlog">
    Sending telemetry is available for workspaces in the EU region. For a US workspace, [contact us](https://cal.com/superlog/yc).

    Install the [Superlog MCP server](/assistants/claude) in Claude Code, Cursor, Codex, or another agent, and open it in your repository. Sign in as a workspace owner or admin, so the agent can turn on error notifications.
  </Step>
  <Step title="Create an API key for source maps">
    If you have a browser app, create a workspace API key under **Settings → API keys** and set it as `SUPERLOG_API_KEY` in your shell. The build uses it to upload source maps. The agent creates the ingest keys itself.
  </Step>
  <Step title="Paste the prompt">
    Paste the prompt below. The agent stops and asks you when it needs you to deploy, approve a connection, or choose a channel.
  </Step>
</Steps>

```text Setup prompt
Set up Superlog for this repository so the team knows about every failure that
affects users. Superlog is at https://superlog.sh and you have its MCP server.
A workspace API key for source map uploads may be in SUPERLOG_API_KEY.
Never commit a key.

Work in these steps. After each step, tell me what you did. When a step needs me,
stop and ask.

1. Inventory
   - List every service in the repository: HTTP APIs, workers, scheduled jobs,
     and browser frontends. Give each a short, stable service name.
   - Map how they call each other: HTTP and gRPC calls, queues and topics,
     background jobs, and calls from the browser to the backend.
   - Call list_integrations and list_services to see what is already connected
     and which services already send telemetry.

2. Ingest keys
   - Create one ingest key for the backend services and one for each browser
     app with create_ingest_key. Name each key after what uses it.
   - Add the settings to the example environment file with placeholder
     values. Tell me where to set the real values for each deployment, or set
     them in the secret manager the project already uses.

3. Backend services: OpenTelemetry
   - Use the official OpenTelemetry SDK for each service's language, with
     automatic instrumentation for its framework, HTTP clients, database
     clients, and queues.
   - Configure the exporters only with environment variables:
       OTEL_EXPORTER_OTLP_ENDPOINT=https://superlog.sh/api/ingest
       OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
       OTEL_EXPORTER_OTLP_HEADERS=x-api-key=<ingest key>
     Send traces, metrics, and logs.
   - Set service.name, service.version, and deployment.environment.name on
     every service.
   - Connect the existing logger to the OpenTelemetry logs SDK so each record
     carries its trace and span IDs. Keep console output.
   - Record unhandled exceptions on the active span as exception events, and log
     them at error level, so Superlog groups them into error issues.
   - Add spans around the few operations that matter most to users, such as
     checkout or sign-in, if automatic instrumentation does not cover them.
   - Start the SDK before the app loads other modules. Flush and shut it down
     when the process exits.

4. Browser frontends: Superlog browser SDK
   - Install @superlog/browser, and @superlog/react for React apps. Follow
     https://docs.superlog.sh/guides/browser.
   - Call init before the app renders, with service, release, environment, the
     browser app's ingest key as ingestKey, and
     endpoint: "https://superlog.sh/api/ingest".
   - Use the React error boundary and router instrumentation for React apps.
   - Upload source maps in the build with @superlog/sourcemaps and
     SUPERLOG_API_KEY. Use the same release value as init.

5. Connect requests across services
   One user action must show up as one trace, from the browser through every
   service it reaches.
   - Use W3C trace context (traceparent and tracestate) everywhere.
   - Browser to backend: set tracePropagationTargets in the browser SDK to the
     app's API origins. Allow the traceparent and tracestate headers in the
     API's CORS settings.
   - Service to service: check that every outgoing HTTP and gRPC client is
     instrumented so it sends traceparent, and that every server continues it.
     Check that proxies, gateways, and load balancers pass the headers through.
   - Queues and background jobs: inject the trace context into each message's
     headers or attributes when it is sent, and extract it when it is
     processed, so the job's spans join the trace that enqueued it. Use the
     instrumentation library for the queue if there is one.
   - Request IDs: if the app already has a request ID, add it to the active
     span as an attribute and to every log record. Return the trace ID in a
     response header so support can find a user's request.
   - Verify: after step 6, find a trace for a user action that crosses services
     with query_traces, open it with get_trace, and confirm it has spans from
     the browser and every service involved. Fix any break you find.

6. Verify the data
   - Run the project's checks. Then ask me to deploy, or to run the services
     locally with the settings, and send some traffic.
   - Confirm each service with list_services, query_traces, query_logs, and
     query_metrics. Note the real metric names, routes, and attribute names.
     Build everything below from data you have seen, not from guesses.

7. Slack and error notifications
   - If Slack is not connected, call start_integration_connection for Slack and
     wait for me to approve it. Then call list_slack_channels.
   - Ask me which channel gets alerts and which gets error notifications.
   - Turn on error notifications for that channel with
     update_error_notifications.

8. Dashboards
   - Create one "Service health" dashboard for the whole system: requests per
     service, error spans per service, p95 latency per service, a list of recent
     error logs, and a list of recent error traces. Add a dashboard variable for
     deployment.environment.name.
   - Create one dashboard per service: throughput, errors, and p50, p95, and p99
     latency by route; the slowest routes as a table; database and outgoing
     call latency; runtime metrics such as memory and CPU if the service sends
     them; and a list of its error logs.
   - Query each widget's data before you add it. Arrange the widgets with
     update_dashboard_layout so the most important charts are at the top.

9. Alerts
   - Create only alerts someone should act on. Each alert name says what is
     broken. Superlog alerts compare one value with a threshold. They cannot
     divide two values, so use counts and percentiles.
   - For each service, cover these cases where they apply:
     a. Down: span count below 1 over 10 minutes, for services with steady
        traffic.
     b. Failing requests: error span count above a threshold.
     c. Slow: p95 span duration above a threshold on the main routes.
     d. Crashes: fatal logs above 0.
     e. Backlog: queue depth or job lag metrics above a threshold, if the
        service has them.
   - Set each threshold from the last 7 days of data so it does not fire on
     normal peaks. Group by service and turn on alerting for each group where
     it helps.
   - Check every alert with preview_alert before create_alert. Show me the rule,
     threshold, and preview, and wait for my approval. Send alerts to the alert
     channel.

10. Synthetic checks
   - Create a check for each public health endpoint and the main pages. Run
     every minute, retry once, and alert after 2 failed runs. Assert a 2xx
     status and a response time, a JSON status field if the health endpoint
     returns one, and a TLS certificate that expires in more than 14 days.
     Send failures to the alert channel.

11. Terraform
   - If the repository already manages infrastructure with Terraform, offer to
     add the output of export_terraform to it. Otherwise skip this step.

Finish with a table of every service, ingest key, dashboard, alert, and
synthetic check you created, and a list of anything you could not set up and
why.
```

The agent shows you each alert before it creates it. Review the thresholds. You know which numbers mean users are affected.

## Checklist

Work through these steps for each service you run. Each one links to the page that covers it.

<Steps>
  <Step title="Send telemetry">
    Send logs, traces, and metrics from the service. Set `service.name` and `deployment.environment.name` so Superlog can group and filter by them. Connect logs to traces so each log record carries its trace and span IDs.

    See [Collect telemetry](/collect-telemetry/overview).
  </Step>

  <Step title="Connect requests across services">
    Pass W3C trace context (`traceparent`) on every call between services, including from the browser to your API and through queues and background jobs. Then one user action shows up as one trace. If your app has a request ID, add it to spans and logs.

    See [Traces](/telemetry/traces) and [Browser and React](/guides/browser).
  </Step>

  <Step title="Connect Slack">
    Slack is where alerts, error notifications, and synthetic check failures go.

    See [Slack](/integrations/slack).
  </Step>

  <Step title="Turn on error notifications">
    Superlog groups exceptions into issues on its own. Turn on notifications so a Slack channel hears about each new error and each regression. Resolve or silence issues from the Slack message.

    See [Errors](/telemetry/errors#slack-notifications).
  </Step>

  <Step title="Add alerts">
    Add an alert for each signal that means users are affected, such as a spike in error logs or slow requests on a key endpoint. Preview each alert before you save it.

    See [Alerts](/telemetry/alerts).
  </Step>

  <Step title="Add synthetic checks">
    Add a check for each public endpoint and health route. Superlog requests it on a schedule and posts to Slack when it fails.

    See [Synthetic checks](/telemetry/synthetics).
  </Step>

  <Step title="Build a service dashboard">
    Chart request rate, errors, and latency for the service. Add a variable for the environment so one dashboard covers all of them.

    See [Dashboards](/telemetry/dashboards).
  </Step>
</Steps>

If you already manage infrastructure with Terraform, you can keep your alerts, dashboards, and synthetic checks there too. See [Terraform provider](/developer/terraform).
