Responder cuts through the noise of production incidents by automatically investigating alerts the moment they fire. Instead of paging an engineer to triage a Sentry crash or a Datadog anomaly at 3 AM, Responder dispatches an AI agent that gathers context, reasons through evidence, and delivers a structured report — complete with root-cause analysis and, when possible, a remediation pull request.

## How it works

When an alert arrives, Responder's worker picks up the job, spins up an isolated sandbox, and runs a versioned investigation agent against your connected data sources. Within minutes you get a structured report in your dashboard, a filed issue, a Slack update, and optionally a draft PR — all without a human touching a keyboard.

```
Alert fires → Responder agent investigates → Report + Issue + optional PR
```

The investigation is fully reproducible: every run pins the exact agent version and runtime profile that were active when the alert arrived, so replaying a past incident produces a consistent and auditable result.

## Key capabilities

**Supported alert triggers**

Responder watches the sources your team already uses:

- **Sentry** — project error alerts and issue webhooks
- **Datadog** — monitor alerts delivered via webhook
- **Dash0** — failed checks and observability alerts
- **Slack** — selected channels, including CloudWatch `ALARM` messages posted there

**Context sources**

Once an investigation starts, the agent draws on more than 15 integrated tools to build a complete picture: GitHub (code and pull requests), Sentry, Datadog, Dash0, PostHog, Grafana, Axiom, AWS, Google Cloud, Upstash, Langfuse, Supabase, Vercel, ClickStack, Linear, and any custom MCP server you connect.

**Investigation outputs**

Every completed investigation produces one or more of the following:

| Output | Description |
|---|---|
| Structured report | Root-cause analysis with evidence and reasoning trace |
| Issue | Filed and linked to the triggering alert |
| Slack update | Posted to the channel or thread of your choice |
| Remediation PR | Draft pull request opened against the affected repository |

## Architecture overview

Responder runs as two cooperating services that share a single Postgres database:

**Control plane** — The dashboard and API you interact with directly. It handles authentication, workspace configuration, integration setup, webhook ingestion, and job scheduling. The React UI is served from the same origin as the API.

**Worker** — A background service that claims investigation jobs from the queue, resolves the pinned agent and runtime profile, and runs the investigation inside an isolated Daytona sandbox. The worker communicates with model providers and connected context sources, then persists the resulting trace and report back to the database.

```
Browser → control-plane (dashboard + API)
                │
                └── enqueues jobs → worker → sandbox + model + providers
                         │
                    Postgres (shared)
```

Both services read from the same database, use the same encryption key for stored credentials, and share an internal bearer token. You can deploy them on any infrastructure that runs Node.js or containers.
