Superlog reads your Sentry errors and issues to find what broke and who it affects. It never changes issues, alerts, or settings in Sentry.

## What Superlog reads

- Issues, events, stack traces, and traces.
- Projects, releases, and environments.

## Connect Sentry

Open **Setup → Sources**, click **Add source**, choose **Sentry**, and click **Continue to Sentry**. Or, in **Integrations**, click **Add** on Sentry. Approve the Superlog app for your Sentry organization. Superlog syncs the projects your account can see.

The Sentry card in **Integrations** shows whether the connection works and how many projects it found. If a check fails, select the card to reconnect.

## How findings use Sentry

Superlog reads Sentry in every workspace that connects it, whether or not other telemetry reaches Superlog.

- Every minute, Superlog lists your organization's unresolved errors with events since the last read. The first read takes the 25 busiest issues of the last week.
- An issue Sentry marks new, regressed, or escalating is a problem to investigate. Info and debug messages and performance issues are left out.
- A Sentry issue is already one problem, so Superlog does not group it further. Its Sentry project is the service name you can skip in [Finding settings](/findings/settings#general).
- A dismissed issue is looked at again when Sentry marks it regressed or escalating, when its hourly count reaches three times the count at dismissal and at least 10 an hour, or when it still has events after the cooldown.

During investigations, Superlog reads events, stack traces, and traces from Sentry for evidence.

## Start automations from Sentry

Add a Sentry trigger and pick up to 100 projects:

- **New issue** when Sentry creates an issue.
- **Issue regression** when a resolved issue comes back.
- **New issue or regression** for both.

The run is titled with the Sentry short ID and issue title. See [Triggers](/automations/triggers#sentry).

The **Alert on critical Sentry issues** and **Fix regressions** templates are a good starting point. See [Templates](/automations/templates#bug-triage).

## Let agents read Sentry

Add Sentry as a connector so the agent can look up issues, events, traces, and projects through Sentry's MCP server. This is useful for automations triggered from Slack or a schedule, such as matching a support report to a known error.

Tag mode can read Sentry when you turn it on for tag mode.

## Self-hosted setup

Self-hosted deployments need their own public Sentry integration.

| Setting | Value |
|---|---|
| Redirect URL | `<public-url>/api/integrations/sentry/callback` |
| Webhook URL | `<public-url>/api/webhooks/sentry` |
| Resource subscriptions | `issue.created`, `issue.unresolved` |
| Permissions | Organization: Read, Project: Read, Event: Read |
| Verify install | Enabled |

Set `SENTRY_APP_SLUG`, `SENTRY_CLIENT_ID`, and `SENTRY_CLIENT_SECRET`. Superlog checks every webhook signature against the client secret. See [Environment variables](/self-hosting/environment).
