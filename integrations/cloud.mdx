Responder supports AWS and Google Cloud as read-only investigation context. When an agent runs, it can inspect alarms, metrics, logs, infrastructure resources, and more — without ever storing long-lived credentials. Both integrations use temporary, automatically-rotated credentials scoped to read operations, with explicit denies on secrets and key material.

## AWS

Responder connects to AWS using a CloudFormation-deployed IAM role and STS role assumption. No access keys are stored — Responder obtains and automatically refreshes temporary credentials through STS, keeping your AWS credentials entirely outside the investigation sandbox.

**What Responder can access**

The deployed role attaches the AWS-managed `AIOpsAssistantPolicy`, which grants account-wide read access including:

- CloudWatch alarm configuration and history
- CloudWatch metrics and Logs Insights
- SQS queue attributes
- Lambda configuration and event source mappings
- General read-only AWS API calls via the sandboxed script runner

An explicit deny prevents the role from retrieving Secrets Manager values, SSM parameters, or decrypting KMS ciphertext, regardless of what `AIOpsAssistantPolicy` allows.

**Setting up the AWS integration**

<Steps>
  <Step title="Open Settings → Integrations → AWS">
    Navigate to the AWS integration page in Responder.
  </Step>
  <Step title="Enter your AWS account ID">
    Provide your 12-digit AWS account ID. Responder generates a CloudFormation template that creates the `ResponderInvestigationRole` in your account, scoped to your deployment's broker ARN and a unique external ID.
  </Step>
  <Step title="Deploy the CloudFormation stack">
    Review the generated stack and deploy it in your AWS account. Responder links you to a CloudFormation Quick Create URL, or provides the template as a file download if you prefer manual upload.
  </Step>
  <Step title="Wait for CREATE_COMPLETE">
    Monitor the stack in the AWS CloudFormation console. Once it reaches `CREATE_COMPLETE`, return to Responder.
  </Step>
  <Step title="Verify the connection in Responder">
    Click **Verify** in Responder. Responder performs a test STS `AssumeRole` call to confirm the role is reachable and correctly configured.
  </Step>
</Steps>

<Warning>
The `AIOpsAssistantPolicy` grants account-wide read permissions across all regions. Review the full policy in the CloudFormation template before deploying. The explicit deny on Secrets Manager, SSM parameters, and KMS decryption is enforced at the role level regardless of other policies.
</Warning>

**Routing CloudWatch alarm alerts to Responder**

AWS does not send webhooks directly to Responder. Route CloudWatch alarms through Slack using Amazon Q Developer in chat applications:

1. Configure Amazon Q Developer in chat applications to forward CloudWatch alarm notifications to a Slack channel.
2. In Responder, add that Slack channel as a watched channel on the relevant Agent, and add your AWS account as Agent context.

Responder starts an investigation only for `ALARM` state notifications. `OK` and `INSUFFICIENT_DATA` notifications are acknowledged without starting investigations. AWS alarm investigations preload the CloudWatch, messaging, and serverless investigation guides automatically.

<Note>
This integration currently supports the commercial AWS partition (`arn:aws`) only. GovCloud and China partitions are not supported.
</Note>

## Google Cloud

Responder connects to Google Cloud using Workload Identity Federation tied to your AWS broker role. No service account keys are stored — Responder exchanges the AWS identity for a short-lived Google token and impersonates a dedicated service account for each investigation.

**What Responder can access**

Setup creates a `responder-investigation` service account with the following read-only roles:

| Role | Access |
|---|---|
| MCP Tool User | Use Google's managed MCP servers |
| Cloud Asset Viewer | Read Cloud Asset Inventory |
| Logs Viewer | Query Cloud Logging |
| Monitoring Viewer | Read Cloud Monitoring |
| Service Usage Consumer | Check enabled API state |

Responder exposes only tools that Google's managed MCP servers explicitly annotate as read-only. Customer IAM roles remain the authorization boundary.

**Setting up the Google Cloud integration**

<Note>
Google Cloud setup requires your Responder deployment to run on AWS. Responder uses the same `AWS_INTEGRATION_PRINCIPAL_ARN` broker role configured for the AWS integration. Ensure your AWS integration is set up before connecting Google Cloud.
</Note>

<Steps>
  <Step title="Open Settings → Integrations → Google Cloud">
    Navigate to the Google Cloud integration page in Responder and click **Connect**.
  </Step>
  <Step title="Sign in with Google">
    Sign in with a Google account that has permission to:
    - Enable APIs on the target project
    - Create service accounts and Workload Identity pools
    - Modify project IAM bindings

    Responder requests the Cloud Platform scope with online access only. The token is used solely for setup, then revoked — Responder does not store a refresh token.
  </Step>
  <Step title="Select a GCP project">
    Responder lists the projects visible to your signed-in account. Select the project you want to use as investigation context. Each project is stored as a separate integration account.
  </Step>
  <Step title="Wait for setup to complete">
    Setup runs as a background job and can take up to 15 minutes. Responder enables the required APIs, creates the `responder-investigation` service account, and configures Workload Identity Federation in your project. Track progress directly in the connection dialog — closing your browser does not interrupt setup.
  </Step>
  <Step title="Add Google Cloud as Agent context">
    Once setup completes, select your Google Cloud project connection under **Context** on the Agent configuration screen.
  </Step>
</Steps>

The OAuth callback for Google sign-in is:

```
<public>/api/integrations/gcp/callback
```

**How credentials work during investigations**

Responder assumes the AWS broker role using the connection's stable session name, exchanges the AWS identity for a short-lived Google token via Workload Identity Federation, and impersonates the `responder-investigation` service account. No service account key is ever created or stored.
