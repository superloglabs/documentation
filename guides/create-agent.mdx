An Agent is a standing configuration that watches a trigger source — a Sentry project, a Datadog monitor, a Dash0 alert policy, or a Slack channel — and launches an AI investigation every time an event fires. Each investigation produces a structured report with severity ratings, root cause analysis, a timeline of events, evidence links, and optional pull request remediation. This guide walks you through creating and configuring your first Agent.

<Steps>
  <Step title="Open Agents and start a new Agent">
    Navigate to **Agents** in the left sidebar. Click **New Agent** in the top-right corner of the Agents list. Responder opens the Agent creation form.
  </Step>

  <Step title="Name your Agent">
    Enter a descriptive name (for example, `Backend API — Sentry` or `Payments Service — Datadog`). A clear name helps your team identify which service and trigger source the Agent covers.

    Add an optional description to give teammates extra context about what this Agent investigates.

    <Tip>
      Keep names short enough to read at a glance in the Agents list — aim for under 60 characters. The name can be up to 80 characters.
    </Tip>
  </Step>

  <Step title="Choose a trigger">
    Select the event source that starts an investigation. Responder supports five trigger types:

    <CardGroup cols={2}>
      <Card title="Sentry Issue" icon="bug">
        Select a connected Sentry account and one or more projects. Investigations start on `issue.created` and `issue.unresolved` events — new errors and regressions.
      </Card>
      <Card title="Datadog Monitor" icon="chart-line">
        Select a connected Datadog account and enter one or more monitor IDs. Investigations start when a monitor transitions to an alert state.
      </Card>
      <Card title="Dash0 Alert" icon="bell">
        Select a connected Dash0 account. Investigations start on `alert.ongoing` events from your Dash0 organization.
      </Card>
      <Card title="Slack Channel" icon="slack">
        Select a Slack workspace and a specific channel. Investigations start whenever a new message is posted in that channel — useful for routing PagerDuty or custom alert webhooks through Slack.
      </Card>
      <Card title="Slack Mention" icon="at">
        Select a Slack workspace and optionally restrict which channels Responder listens in. The Agent responds every time someone mentions the Responder bot.
      </Card>
    </CardGroup>

    <Note>
      **Thread** reporting (replying directly to the alert thread) is only available when the trigger is a Slack Channel or Slack Mention. Sentry and Datadog triggers always require an output channel.
    </Note>
  </Step>

  <Step title="Choose a model">
    Select the AI model Responder uses to run investigations. The model dropdown lists all models available in your workspace.

    - **Auto / Instance default** — uses the model configured in your Responder deployment's Model Access settings.
    - **Named model** — uses a specific model (for example, `gpt-4o`). Requires a matching API key configured in Model Access settings, or Responder's included usage allowance.

    You can change the model after saving; the new model applies to future investigations.
  </Step>

  <Step title="Add investigation context">
    Tell Responder which data sources to query when investigating alerts. Select from two categories:

    **Observability and tooling integrations** — toggle on any connected account the Agent should access. Available providers include Datadog, Grafana, PostHog, Sentry, Dash0, Axiom, Upstash, Langfuse, Supabase, AWS, GCP, Vercel, ClickStack, Linear, and custom MCP servers. Each enabled account gives Responder access to that provider's data during investigations.

    **Slack channels** — select specific channels the Agent can search for related messages and historical context.

    **GitHub repositories** — select repositories for code inspection. The Agent reads file contents and commit history to trace root causes back to specific changes. Repositories are also required if you plan to enable pull request remediation.

    <Tip>
      Add every integration relevant to the service you're monitoring. Responder correlates signals across sources, so more context generally produces more accurate root cause analysis.
    </Tip>
  </Step>

  <Step title="Configure reporting">
    Choose where Responder posts investigation results:

    | Mode | Description | Requirement |
    |------|-------------|-------------|
    | **Thread** | Replies to the originating Slack thread | Slack Channel or Slack Mention trigger |
    | **Output channel** | Posts to a designated Slack channel | Slack must be connected |
    | **Both** | Thread reply _and_ channel post | Slack Channel trigger + Slack connected |

    When posting to an output channel, optionally filter by severity so only the issues that matter reach that channel:

    - **SEV-1** — Critical outage or widespread customer impact
    - **SEV-2** — Significant degradation or limited customer impact
    - **SEV-3** — Minor impact with no immediate operational urgency

    Leave all three checked (the default) to receive every investigation result.
  </Step>

  <Step title="Set PR mode">
    Choose how Responder handles code fixes identified during an investigation:

    | Mode | Behavior |
    |------|----------|
    | `disabled` | No pull requests — investigation reports only |
    | `manual` | Responder prepares the diff and PR content; you approve before the PR opens |
    | `always` | Responder automatically opens a pull request as part of the investigation |

    PR mode requires at least one GitHub repository to be selected. If no repository is selected, PR mode defaults to `disabled`.

    <Warning>
      `always` mode opens pull requests without any human review step. Use `manual` mode if you want to inspect diffs before they become open PRs.
    </Warning>
  </Step>

  <Step title="Write Agent instructions">
    Customize the prompt the Agent uses when investigating alerts. The default instructions tell Responder to investigate the root cause, assess severity and customer impact, and post a concise summary with evidence and recommended next steps.

    Extend the default instructions with domain-specific guidance — for example:
    - The primary database or cache layer to check first
    - Known flaky tests or infrastructure quirks to account for
    - Code style conventions for generated pull requests
    - On-call runbooks or escalation policies

    Instructions can be up to 400,000 characters. Changes take effect on the next investigation.
  </Step>

  <Step title="Save the Agent">
    Click **Save**. Responder creates the Agent and enables it immediately. You are redirected to the Agent's run history page.
  </Step>
</Steps>

## Enable and disable an Agent

An enabled Agent reacts to its trigger source in real time. A disabled Agent ignores incoming events.

Toggle an Agent's status from the **Agents list** — use the status switch on the Agent row — or from the **Agent detail page** using the Active/Inactive toggle in the header. Changes take effect immediately; no save is required.

## Edit an Agent

Open the Agent from the Agents list, then click the **Settings** tab. Edit any field and click **Save**.

<Note>
  Editing an Agent creates a new configuration version. Any investigations that are already running finish on the previous version of the configuration. New investigations started after you save use the updated configuration.
</Note>

Editing does not restart the Agent or affect its enabled/disabled state.
