Responder doesn't stop at diagnosing a problem — it can also prepare and open the pull request that fixes it. After identifying an issue during an investigation, Responder analyses the relevant code, assembles a complete git diff, writes a PR title and body, and either opens the PR automatically or queues it for your approval depending on how the Agent is configured. This guide explains the remediation types, the PR mode options, and what to expect when you collaborate on a Responder-generated PR.

## How remediation works

When Responder finishes an investigation it produces one or more remediation options for each issue it identified. A remediation is either a code change or an external action:

<CardGroup cols={2}>
  <Card title="Code Change" icon="code">
    A complete unified git diff targeting one or more connected repositories, paired with an agent-authored PR title and Markdown body. One code-change remediation produces one pull request per repository.
  </Card>
  <Card title="External Action" icon="arrow-up-right-from-square">
    When the fix requires intervention outside of your codebase — for example, updating a feature flag, rotating a secret in a third-party service, or modifying infrastructure configuration — Responder provides a self-contained prompt you can hand to another agent or follow yourself.
  </Card>
</CardGroup>

Remediations appear on the investigation report under each issue. Select the remediation you want to act on, then promote it to a pull request from the dashboard.

## PR modes

Set the PR mode per Agent during Agent creation or editing. The mode controls whether Responder opens PRs automatically.

| Mode | Behaviour |
|------|-----------|
| `disabled` | No pull requests are created. Investigation reports include remediation suggestions, but no code changes are applied. |
| `manual` | Responder prepares the full diff and PR content and makes it available on the investigation report. A PR is opened only when you click **Open PR** from the dashboard. |
| `always` | Responder automatically opens a pull request on GitHub as part of the investigation — no manual approval step. |

<Warning>
  `always` mode opens pull requests against your repositories without any human review. Use `manual` mode if you need to inspect diffs before they become open pull requests.
</Warning>

<Tip>
  Add detailed instructions to your Agent about your team's code style, testing conventions, and any files or directories that should never be modified. The more context you give, the higher the quality of Responder's generated diffs.
</Tip>

## Prerequisites

- At least one GitHub repository must be **connected** to your Responder workspace.
- That repository must be **selected** in the Agent's repository list.
- PR mode must be set to `manual` or `always`.

If no repository is selected on the Agent, the PR mode is automatically set to `disabled` and Responder will not attempt to generate code changes.

## Reviewing and opening a PR in manual mode

<Steps>
  <Step title="Open the investigation report">
    Navigate to the Agent in the dashboard and open the investigation from the Run history tab. Alternatively, follow the link in the Slack notification.
  </Step>

  <Step title="Review the remediation">
    Expand the issue you want to fix and select a remediation. Click **View diff** to inspect the proposed code change before committing to it. The diff includes the full unified patch — `diff --git`, `---/+++` headers, and hunk context — so you can evaluate the change the same way you would review any pull request.
  </Step>

  <Step title="Open the pull request">
    Click **Open PR** on the remediation card. Responder creates the pull request on GitHub using the agent-authored title and Markdown body. The dashboard updates with a link to the open PR.
  </Step>
</Steps>

## Review follow-ups on Responder PRs

After Responder opens a pull request, you and your team can leave inline review comments on the diff as you normally would. Responder monitors unresolved comment threads on its own PRs and acts on them:

1. Responder reads all unresolved review comment threads on the PR.
2. It pushes a follow-up commit to address the feedback.
3. It marks the threads as resolved.

<Note>
  Responder only processes review comments left on PRs it opened. Comments left by humans are handled automatically — Responder reads the comment content and acts on it. If you want to block Responder from acting on a comment, resolve the thread yourself before Responder picks it up.
</Note>

This cycle repeats for each new round of unresolved comments, making it straightforward to iterate on a fix without switching contexts.
