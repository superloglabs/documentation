An Agent is a named, versioned configuration that tells Responder what to watch, how to investigate, and where to send results. Every investigation in Responder is driven by an Agent — it connects your alert sources to your context integrations, your codebase, and your AI model of choice, then controls how the finished report reaches your team.

## What an Agent does

When an alert arrives that matches an Agent's trigger, Responder pins the Agent's current configuration, spins up an isolated worker sandbox, and begins an investigation. The Agent governs every step: which context sources the worker can query, which repositories it can inspect or patch, which AI model it calls, and whether it should open a pull request with a proposed fix.

## Configuration fields

### Name and description

Give each Agent a human-readable **Name** (up to 80 characters) and an optional **Description** (up to 500 characters). Use names that make the Agent's purpose obvious at a glance — for example, `Payment Service – Sentry` or `Infrastructure Alerts – Datadog`.

### Trigger

The trigger defines what causes an investigation to start. Each trigger type connects to one of your integrations and watches a specific scope within it.

| Trigger | Source | What it watches |
|---|---|---|
| `sentry_issue` | Sentry | Fires on `issue.created` and `issue.unresolved` events for selected Sentry projects |
| `datadog_monitor` | Datadog | Fires on alert state changes for selected Datadog monitors |
| `dash0_alert` | Dash0 | Fires on `alert.ongoing` webhooks from a connected Dash0 organization |
| `slack_channel` | Slack | Fires on new messages posted to a watched Slack channel |
| `slack_mention` | Slack | Fires when the Responder bot is @-mentioned in one or more configured channels |

### Model

Select the AI model that runs investigations for this Agent. The available models come from your workspace's model access settings.

### Instructions

Write custom prompt guidance that shapes how the Agent approaches every investigation it runs. Instructions accept up to 400,000 characters, giving you plenty of room to describe your service architecture, preferred investigation style, naming conventions, or anything else that helps the model produce more accurate reports.

### Context sources

Add one or more connected integrations as context sources (`contextAccountIds`). During an investigation the worker queries these sources — Datadog, Grafana, PostHog, Dash0, Sentry, and others — to collect logs, metrics, traces, and product telemetry. You can attach up to 20 context accounts per Agent.

### Repositories

Attach GitHub repositories (`repositoryIds`) to give the worker read access to your code. When PR mode is enabled, the worker can also prepare patches and open pull requests against these repos. You can attach up to 100 repositories.

<Note>
  PR mode requires at least one repository. Responder will not let you save an Agent with PR mode set to `manual` or `always` if no repositories are attached.
</Note>

### Secrets

Add workspace secrets (`secretIds`) that should be injected as environment variables into the investigation sandbox. Secrets are opaque — their real values are substituted only at the network boundary and are never readable inside the sandbox or visible in the investigation trace.

### PR mode

Control whether Responder creates pull requests for proposed code fixes:

- **`disabled`** — Responder never creates pull requests (default).
- **`manual`** — Responder prepares the diff and PR content, but waits for you to approve before publishing.
- **`always`** — Responder publishes pull requests automatically as soon as an investigation finishes.

### Reporting mode

Choose where finished investigation reports are delivered:

- **`thread`** — Posts the report as a reply in the originating Slack thread. Requires a `slack_channel` or `slack_mention` trigger.
- **`output_channel`** — Posts the report to a designated Slack channel. You can optionally filter by severity so that only SEV-1, SEV-2, or SEV-3 reports are posted.
- **`both`** — Posts to both the originating thread and the output channel. Requires a Slack trigger plus an output channel.

### Linear tickets

Enable **Create Linear tickets for new issues** to have Responder automatically queue a Linear ticket for each new issue an investigation finds. You can customize the ticket body using a Markdown template with these variables:

| Variable | Value |
|---|---|
| `{{issue_id}}` | Responder's internal issue identifier |
| `{{issue_url}}` | Link to the issue in the Responder dashboard |
| `{{title}}` | Issue title |
| `{{description}}` | Issue description |
| `{{severity}}` | SEV-1, SEV-2, or SEV-3 |
| `{{evidence}}` | Formatted evidence summary |
| `{{remediation}}` | Recommended remediation summary |

### Initial triage

Enable **Initial triage** to get a quick AI reaction in the Slack channel as soon as an alert arrives — before the full investigation completes. This gives your team immediate context while the deeper investigation runs in the background.

<Note>
  Initial triage is only available when the trigger is set to `slack_channel`.
</Note>

## Agent versioning

<Note>
  Every time you save changes to an Agent, Responder creates a new immutable version. In-flight and queued investigations always use the version they were created with — your changes never affect a run that is already underway.
</Note>

Immutable versioning makes investigations reproducible. When you rerun a completed investigation, it uses the Agent's current active version and the latest repository heads, but the original alert input stays the same. This means you can iterate on your Agent configuration and see exactly how your changes affect results.

---

## Enabling and disabling an Agent

Use the enabled/disabled toggle to pause an Agent without deleting it. A disabled Agent ignores incoming trigger events. Re-enable it at any time to resume investigations.
