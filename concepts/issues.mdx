An issue is a persistent, structured record of a specific problem that Responder has identified. Where an investigation is a single AI analysis run, an issue is the durable artifact that survives across runs. Each time Responder investigates an alert, it either creates a new issue, updates an existing one, or links the investigation to a previously identified issue — building a continuous history of each problem in your system.

---

## Issues vs. investigations

It helps to understand how investigations and issues relate to each other:

- A single **investigation** can create multiple new issues, update existing ones, or link to issues that were first seen in earlier runs.
- A single **issue** can appear across many investigations — each time the same underlying problem recurs, the new investigation links to the existing issue rather than creating a duplicate.

This means the Issues page in your dashboard is your persistent incident record book, while the Investigations list is the log of every analysis run Responder has performed.

## Issue fields

<CardGroup cols={2}>
  <Card title="Title" icon="heading">
    A short, human-readable name for the problem (up to 200 characters).
  </Card>
  <Card title="Description" icon="file-lines">
    A detailed explanation of what the issue is and how it manifests (up to 8,000 characters).
  </Card>
  <Card title="Root cause" icon="magnifying-glass">
    A single sentence that precisely names the code, environment, or infrastructure change responsible for the issue.
  </Card>
  <Card title="Severity" icon="triangle-exclamation">
    One of three levels assigned by the investigating model:
    - **SEV-1** — Critical
    - **SEV-2** — High
    - **SEV-3** — Moderate
  </Card>
  <Card title="Timeline" icon="clock">
    An ordered sequence of events (up to 30 entries) describing how the incident unfolded, with a title and one-sentence description per entry.
  </Card>
  <Card title="Evidence" icon="link">
    A collection of linked sources — alerts, Sentry issues, Datadog monitors, GitHub files, Slack messages, and more — each with a title, detail text, optional URL, and optional file and line reference.
  </Card>
  <Card title="Remediations" icon="wrench">
    One or more concrete remediation options. A `code_change` remediation includes a full unified git diff and pull request content. An `external_action` remediation includes a self-contained prompt for a human or downstream agent.
  </Card>
  <Card title="Linear ticket" icon="ticket">
    If Linear integration is enabled on the triggering Agent, a link to the automatically created Linear ticket appears here.
  </Card>
</CardGroup>

## Recurrences

When a new investigation finds evidence that matches an already-known issue, Responder links the investigation to the existing issue instead of creating a duplicate. This recurrence relationship:

- Preserves the full history of every time the problem appeared.
- Lets you see at a glance how often an issue recurs and whether previous remediations actually resolved it.
- Keeps your Issues list clean — one issue per problem, no matter how many times it has triggered an alert.

The Responder model checks for existing issues using `search_existing_issues` before deciding whether to create a new record or attach to an existing one.

---

## Archiving issues

Once you have resolved a problem, archive the issue to remove it from your active issues view. Archived issues remain in the system and can be referenced by future investigations if the problem recurs.

---

## Linear integration

When you enable **Create Linear tickets for issues** on an Agent, Responder automatically queues a Linear ticket request for each new issue an investigation produces. The ticket body is rendered from a customizable Markdown template.

The default template looks like this:

```markdown
## Responder issue
[{{issue_id}}]({{issue_url}})

## Description
{{description}}

## Evidence
{{evidence}}

## Recommended remediation
{{remediation}}
```

You can customize this template on the Agent configuration page. The following variables are available:

| Variable | Description |
|---|---|
| `{{issue_id}}` | Responder's internal identifier for the issue |
| `{{issue_url}}` | Direct link to the issue in the Responder dashboard |
| `{{title}}` | Issue title |
| `{{description}}` | Full issue description |
| `{{severity}}` | SEV-1, SEV-2, or SEV-3 |
| `{{evidence}}` | Formatted summary of evidence sources |
| `{{remediation}}` | Summary of the recommended remediation |

<Tip>
  Ticket creation is handled by a separate background job after the investigation finishes. The resulting Linear ticket identifier and link are saved back to the issue record in Responder, so you can navigate from either system.
</Tip>
