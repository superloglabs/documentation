An investigation is the core unit of work in Responder. When an alert arrives and matches a configured Agent, Responder starts an investigation: a fully automated AI analysis run that queries your logs, metrics, traces, code, and Slack history, then produces a structured report with severity ratings, root causes, timelines, evidence, and optional code remediations. Every investigation is traceable, reproducible, and tied to a persistent issue record.

---

## What happens during an investigation

<Steps>
  <Step title="Alert arrives and Agent configuration is pinned">
    A provider event (a Sentry issue, a Datadog monitor alert, a Dash0 webhook, or a Slack message) reaches the Responder control plane. The control plane validates and normalizes the payload, matches it to an Agent, and pins the Agent's current active configuration version. From this point forward, configuration changes cannot affect this run.
  </Step>
  <Step title="Worker claims the job and creates an isolated sandbox">
    A background worker picks up the durable job from the queue and spins up an isolated repository workspace. GitHub credentials stay outside the sandbox — Responder streams selected repository snapshots into the workspace without exposing raw credentials to the model.
  </Step>
  <Step title="Agent queries connected context sources">
    The worker selects the applicable prompt sections based on connected integrations and investigation mode, then the model begins querying your context sources: logs, traces, and metrics from Datadog, Grafana, Dash0, PostHog, and others; code from attached repositories; Sentry events; and Slack conversation history. Each tool call is recorded in the investigation trace.
  </Step>
  <Step title="Agent produces a structured report">
    After gathering evidence, the model calls `submit_investigation_report` exactly once with a structured result: a headline, a summary narrative, and a list of issues — each with severity, root cause, timeline, evidence, and remediations. The report is saved to the database and issues are created or linked.
  </Step>
  <Step title="Report is delivered">
    Responder posts the report to the Responder dashboard and to Slack according to the Agent's reporting mode. If PR mode is `always` or `manual`, separate jobs publish or stage the prepared code patches for any `code_change` remediations.
  </Step>
</Steps>

## Investigation report structure

Each investigation produces a structured report with the following fields.

### Headline and summary

- **Headline** — A plain-text summary of the investigation in one line (up to 200 characters).
- **Summary** — A narrative description of what the investigation found, up to 2,000 characters.

### Issues

A report can contain up to 20 issues. Each issue includes:

<CardGroup cols={2}>
  <Card title="Title & description" icon="tag">
    A short title and a detailed description of the problem.
  </Card>
  <Card title="Root cause" icon="magnifying-glass">
    A single sentence naming the exact code, environment, or infrastructure change that caused the issue.
  </Card>
  <Card title="Severity" icon="triangle-exclamation">
    One of three severity levels:
    - **SEV-1** — Critical
    - **SEV-2** — High
    - **SEV-3** — Moderate
  </Card>
  <Card title="Timeline" icon="clock">
    An ordered sequence of events (up to 30 entries) that explains how the incident unfolded. Each entry has a title and a one-sentence description.
  </Card>
  <Card title="Evidence" icon="link">
    Linked sources — including alerts, Sentry, Datadog, Dash0, GitHub, Slack, AWS, GCP, Grafana, PostHog, Axiom, ClickStack, Upstash, Langfuse, Supabase, Vercel, and others — each with a title, detail text, optional URL, and optional file and line reference.
  </Card>
  <Card title="Remediations" icon="wrench">
    One or more concrete remediation options, each of type `code_change` (a full unified git diff plus ready-to-publish PR title and body) or `external_action` (a self-contained prompt for a human or downstream agent to act on).
  </Card>
</CardGroup>

## Investigation statuses

| Status | Meaning |
|---|---|
| **Running** | The worker is actively investigating. Tool calls and model steps are accumulating in the trace. |
| **Completed** | The investigation finished and a report was saved. |
| **Failed** | The investigation encountered an unrecoverable error. The trace is preserved for diagnostics. |

---

## Reruns

You can rerun any completed investigation from its detail page in the dashboard. A rerun:

- Reuses the **original alert input** — the same provider event that triggered the first run.
- Uses the Agent's **current active configuration** and the **latest repository heads**.
- Replaces the investigation's report and trace with the new run's output.
- Leaves previous issue records intact and accessible.

<Note>
  Each rerun counts against your organization's monthly investigation allowance, just like any other investigation run.
</Note>

---

## Investigation trace

Every investigation stores a full trace of the model's tool calls and reasoning steps. The trace lets you understand exactly what evidence the model looked at, which tools it called, and how it arrived at its conclusions.

<Tip>
  The trace is available from the investigation detail page. Operators deploying Responder can access the raw stored trace for deeper diagnostics; the tenant-facing view omits the initial composed runtime instructions for security reasons.
</Tip>
